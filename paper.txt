Introduction
In many cases, healthcare suffers from the way patient information is stored and shared. As each hospital/clinic operates its own system for these purposes, it has been a challenge to transfer patient records between healthcare facilities. Even if connectivity is improved, as in the Wireless Access for Health (WAH) project, exchanging information between different systems remains a challenge. WAH is a non-government organization that aims to improve the healthcare system in the Philippines by giving its partner hospitals/clinics connectivity to build a more integrated system (Arnaout et al., 2014). However, because the patient records system is diverse (HIMS, etc.), the records cannot be shared because of the format used. This in turn results in slow care and information inconsistency. 
The problem of exchanging data is a national problem that is targeted by the Universal Health Care (UHC) Act. The UHC Act requires the implementation of interoperable information systems and standardized health data collection (Republic Act No. 11223, 2019) This project builds upon the baseline interoperability system designed by (Cecilio et al., n.d.) by taking further through the full implementation of HL7 Fast Healthcare Interoperability Resources (FHIR) standard. The previous system serves as a baseline system, which provides connectivity. However, the previous system does not have a data standard that can be shared and understood by all participating systems. 
To bridge this gap, this thesis focuses on FHIR mapping, which transforms the current local data formats into standardized models such as Patient, Observation, and Condition. This enables the effective sharing and interpretation of patient data with the same meaning between healthcare systems. The solution proposed therefore acts as an intermediary system that facilitates the flow of data between existing applications and ensures that the data shared is in a standardized format. As noted in Sinaci et al. (2023), the integration of FHIR mapping, compliance, and system integration aims to increase the effectiveness of patient data usage, consistency, and availability of patient records as mentioned throughout the WAH network. 



	


 
Project Context
Healthcare in the Philippines currently faces a critical fragmentation challenge where patient information is trapped in isolated "data islands." While organizations like Wireless Access for Health (WAH) have improved physical connectivity, the digital systems used by partnered facilities, including HIMS, operate with incompatible data formats. This lack of a common language creates a significant hurdle when patients are referred between clinics and Department of Health (DOH) hospitals using systems like iHOMIS. When these records cannot be shared automatically, the result is a reliance on slow, manual processes that increase the risk of "garbage in, garbage out" data pollution and delay life-saving care.
Our project, WAH4PCE: An AI-Driven Automation Layer for PH Core FHIR Interoperability, is a direct technical response to this bottleneck. While previous batches (Cecilio et al., n.d.) established a baseline interoperability server and the core Philippine (PH) Core FHIR formats, the process of translating legacy records into those formats still relies heavily on human gatekeeping and manual verification. Our team bridges this gap by introducing an intelligent automation layer that serves as a Local Health Information Exchange (LHIE). This system is designed to act as the primary connection point between legacy WAH systems and the standardized DOH network, ensuring that data moves with "liquidity" and consistent clinical meaning.
The urgency of this project is heightened by the current national landscape. Although the Universal Health Care (UHC) Act mandates standardized data submission to the National Health Data Repository (NHDR), the development of this national infrastructure is currently on hold following changes in leadership. This creates a critical need for Local Government Units (LGUs) and organizations like WAH to lead the way by establishing their own FHIR-powered interoperability platforms. Our system achieves this by utilizing a modern tech stack. This stack consists of Go (Golang) for high-speed processing, MongoDB for native FHIR storage, and Next.js for administrative oversight.
Central to our solution is an AI-driven Mapping Engine that operates via a Model Context Protocol (MCP) server. This AI agent automatically parses legacy records and maps them to the PH Core FHIR standards established by the "Batch 1 WAH4PC" team, removing the need for manual re-encoding. To ensure the system is production-ready, we implement automated validation tools that verify the accuracy of every record before it reaches a DOH endpoint. While our team focuses exclusively on the automation and translation logic, the system is designed to seamlessly integrate with the security and encryption protocols provided by a separate project group to ensure full compliance with the Data Privacy Act of 2012.
Ultimately, our project goal is to deliver a functional, production-caliber proof-of-concept (POC) that demonstrates how WAH systems can seamlessly talk to DOH systems today. By automating the path to FHIR compliance, we provide WAH and its partners with the technical tools needed to fulfill the vision of the UHC law. This ensures that a patient’s record can follow them securely and instantly from a primary care clinic to a tertiary hospital.







Statement of the Problem
The primary problem is the lack of an automated, intelligent connection between WAH legacy systems and the standardized DOH EMRs (iHOMIS), preventing the realization of a functional Local Health Information Exchange.
Specifically, this study aims to answer the following problems:
•	How can an AI-driven Integration Platform as a Service (iPaaS) be designed to replace manual data mapping and resolve format clashes between WAH legacy systems and DOH systems?
•	How can this intelligent middleware facilitate the bidirectional, automated movement of records between WAH-partnered clinics and DOH-standardized hospitals?
•	How can automated validation and filtering mechanisms be integrated into the exchange environment to prevent "garbage in, garbage out" data pollution?
•	What technical safeguards can be implemented within the middleware to ensure explicit patient authorization during automated data movement, thereby avoiding "implied consent" violations under the Data Privacy Act?











Objectives 
The main objective is to design and implement an AI-driven automation layer that connects WAH-partnered systems to DOH EMRs (iHOMIS) using the PH Core FHIR standard.

•	To establish an automated interoperability bridge: Connect WAH facilities and DOH platforms by translating legacy records into the required formats.
•	To build an intelligent iPaaS gateway: Serve as the automated routing hub that sits between WAH facilities and DOH platforms, managing the API handoffs.
•	To develop a structural validation tool: Check all AI-translated records against the required data schemas (PH Core FHIR or DOH proprietary formats) to ensure data consistency and accuracy before transmission.
•	To implement Consent-as-Code: Integrate a metadata-based "Consent Flag" check within the ADAPT engine to block any unauthorized data exchange.




 

Significance of the Project
This project offers significant benefits by enhancing healthcare efficiency and patient safety within the Wireless Access for Health (WAH) network. The specific groups that will benefit from this project are:

•	For WAH and DOH: This project provides the first automated "proof of concept" (POC) that legacy local systems can communicate with national DOH systems, proving that interoperability is possible even while national infrastructure is on hold.
•	For Healthcare Staff: By automating the translation, nurses and IT staff no longer must manually re-encode data or fix inconsistent formats when referring patients between clinics and hospitals.
•	For Patients: Patients benefit from "data liquidity," where their medical history follows them instantly from a rural clinic (using WAH4H) to a government hospital (using iHOMIS).








Scope and Limitations
Scope:
•	AI Automation Engine: The project focuses on building the AI logic that parses data and maps it to the PH Core FHIR resources provided by Batch 1 WAH4PC.
•	Hybrid Data Training: The AI Engine will be trained using both PH Core FHIR standards and DOH-specific EMR formats to ensure high mapping accuracy between legacy systems and national standards.
•	DOH System Integration: The system acts as the bridge specifically for iHOMIS, enabling WAH systems to "talk" to DOH-standardized EMRs.
•	iPaaS Middleware Integration: The ADAPT system operates strictly as an Integration Platform as a Service (iPaaS). Rather than serving as the central database itself, it functions as the intelligent routing middleware that sits between the DOH endpoints (iHOMIS) and the WAH network, facilitating the secure, automated movement and translation of data.
•	Automated Validation: Implementation of AI-driven "cleaners" to standardize and validate data during the exchange process.
•	The system includes automated "Consent-as-Code" checks and structural FHIR validation for WAH4H and DOH IHomis data formats.

Limitations:
•	Static Data Standards: The project will not create new FHIR formats; it relies strictly on the PH Core standards that were already established and complying with the PhilHealth guidelines.
•	External Dependencies: System testing is contingent upon the availability of mock endpoints for the WAHpatients and WAH hospital modules being developed by other teams.
•	Testing with Dummy Data: Due to privacy laws, We do not have direct access to live DOH or WAH production databases, our team will develop functional dummy system endpoints simulating an iHOMIS environment and a WAH hospital environment. These dummy systems will be used strictly to validate the iPaaS data exchange and demonstrate the bidirectional transformation capabilities.
•	The validation tool checks for structural accuracy and missing fields but does not verify the clinical truth of the medical data provided by the source system.


 
Review of Related Literature / Systems
The landscape of healthcare is undergoing significant metamorphosis driven by digital transformation. This evolution, while promising enhanced efficiency and patient care, hinges on various factors, including technology acceptance and the effective implementation of digital tools. 
One of the pioneering studies that shed light on this shift in the industry is the work of Nassr, Al-Shamayleh, and Al-Shboul (2023). The authors investigate various aspects of how healthcare professionals and patients are adopting new technologies. Specifically, the authors investigate the factors that make healthcare professionals more or less likely to adopt these technologies.
Another study that investigates this same topic but with a focus on the local area is by Llanes et al. (2024), who investigate the current state of the Electronic Health Record (EHR) system in the Philippines. The authors reveal valuable insights into the current state of the EHR system in the Philippines. Furthermore, because there are some disconnected EHR systems within the Philippines, there is a recognized need for a system that can provide a standard system for the data to be exchanged between these disconnected systems.
The digital tools can be further seen in the work of Singh et al. (2024), who discuss the potential of artificial intelligence to improve health outcomes through earlier and more accurate diagnoses.
The benefits and the challenges of Electronic Health Records (EHRs) are discussed by Simbo.ai (2023). The authors explain how these systems can lead to improved health information management and health care professionals’ workflows, but also present issues with interoperability between different health systems. Most health systems utilize slightly different structures of their internal data from others in the industry, preventing interoperability between these health records databases.
To overcome these interoperability challenges, the healthcare industry has used the HL7 Fast Healthcare Interoperability Resources (FHIR) standard (Adegoke et al., 2025). HL7 FHIR allows healthcare data to be represented in a standard format using modular resources. Using this standard, systems can exchange data with semantic interoperability. FHIR requires a full mapping from the existing databases to the FHIR standard to enable interoperability between these two systems. Several research studies have explored how to create interoperable and reusable health data using the FHIR standard (Sinaci et al., 2023). Additionally, there are several studies exploring the semantic issues of FHIR and implementing the FHIR standard within EHR systems (Amar et al., 2024). These solutions will eliminate data silos and enable better communication between systems.
Finally, the broader implications for healthcare quality and safety are discussed by Alshurideh et al. (2024). Their work highlights how digital transformation improves service delivery, particularly when systems are integrated and capable of sharing accurate data. The effectiveness of these improvements depends on the ability of systems to communicate reliably, further reinforcing the importance of standardized interoperability frameworks such as FHIR. 
Through reviewing the literature, it is evident that there is both a global and local movement toward the digitization of healthcare. The literature discusses, for instance, the acceptance of technology in healthcare (Nassr et al., 2023), the challenges of implementing Electronic Health Records in healthcare facilities (Charalambous, 2024), the role that advanced technologies play in improving healthcare outcomes (Singh et al., 2024), and the impact of digitization on healthcare (Alshurideh et al., 2024). Furthermore, systems like CHITS, and iHOMIS have allowed for the digitization of certain processes within the Philippines (Inquirer Business, 2025; Ongkeko et al., 2016; Philippine Council for Health Research and Development, n.d.; Scribd, n.d., 2021; UIJRT, n.d.) but also demonstrate the limitations of such systems implemented alone. Thus, the literature indicates a need for a system that provides interoperability for the country’s healthcare systems. Such interoperability could be achieved through the implementation of a system that maps each healthcare system to the FHIR standard, which would guarantee compliance with the UHC law (Philippine Statistics Authority, 2025; Scribd, 2021) and lead to the integration of the entire Philippine healthcare system.
According to research by Nan and Xu (2023), the biggest obstacle to the digital transformation in healthcare is the existence of so-called data islands. Even as medical records are increasingly going digital, the data are still confined to heterogeneous Information Technology (IT) systems that lack a common language. This fragmentation does not allow providing coordinated care and narrows the utility of clinical decision-support tools (Nan & Xu, 2023). 
The researchers refer to Fast Healthcare Interoperability Resources (FHIR) as the most promising solution to this issue. Unlike the previous messaging standards, which were complex and rigid, FHIR leverages the current web technologies i.e. RESTful API and modular Resources (Nan and Xu, 2023). They consist of standardized building blocks, including Patient, Medication and Procedure, which are shared between different systems in order to share certain bits of information efficiently. Flexibility of FHIR is highlighted in the literature, with the mention of the fact that it can be applied to various platforms, such as mobile health apps and cloud systems (Nan and Xu, 2023). 
Nan and Xu (2023) formulate three areas of critical importance on the basis of a systematic review of 85 scholarly articles: 
•	Data Standardization and Mapping: A sizeable portion of the literature is focused on the transformation process, i.e. how to convert the current legacy data, e.g. CDA or HL7 v2, to FHIR-conformant data. This is critical in making sure that information from various time periods and systems can be successfully merged (Nan & Xu, 2023). 
•	Data Management and Storage: The review explains the architecture of FHIR servers and emphasizes the need to have robust architecture that can address large-scale "Big Data" and maintain high rates of security and privacy controls to protect confidential patient information (Nan & Xu, 2023). 
•	Clinical Services Data Interoperation: This paper goes beyond mere technical exchange to emphasize "semantic interoperability." This has been determined as the ability of systems to not only communicate its content but also the meaning and react to it, which will allow the provision of higher-level services like real-time patient tracking and research across institutions (Nan & Xu, 2023). 
The proposal of a General FHIR Practice Guideline (FHIR PG) is one of the important contributions of this research. In their argument, Nan and Xu (2023) argue that standardization is not a technical undertaking but a team effort. Their model defines the roles of different groups of stakeholders to be successful: to prevent the non-compatibility of different versions of FHIR, the standardizers need to create particular Implementing Guides; the system provider needs to create the infrastructure and servers to store such data; and the service provider (app developers) needs to create user-facing tools to transform this data into improved clinical outcomes (Nan & Xu, 2023).
The transition from manual paper-based reporting to electronic health records (EHRs) in the Philippines, led by initiatives like Wireless Access for Health (WAH), necessitates a theoretical framework for seamless data exchange. According to Vorisek et al. (2022), the FHIR standard serves as this framework by utilizing modern web technologies such as RESTful APIs and JSON to ensure that health data adheres to the FAIR Principles (Findable, Accessible, Interoperable, and Reusable). In the context of the Philippines' Universal Healthcare Act, the literature emphasizes that "data liquidity"—the ability of data to move securely and meaningfully between systems—is the next frontier for digital health. Vorisek et al. argue that FHIR’s "resource" building blocks allow for the modular development of health systems, which aligns with WAH's open-source philosophy. However, the literature also warns of significant bottlenecks, including the "versioning" of FHIR resources and the legal complexities of cross-institutional data sharing, which remain primary challenges for the Philippines as it seeks to harmonize fragmented local health information into a unified national repository.
The landscape of digital health in the Philippines is governed by DOH-PHIC Joint Administrative Order (JAO) No. 2021-0002, which institutionalizes the Mandatory Adoption and Use of National Health Data Standards for Interoperability. This policy serves as the regulatory backbone for the Universal Health Care (UHC) Act, recognizing that "seamless and interoperable health services" are essential for evidence-based sectoral planning. According to the JAO, the current inconsistent adoption of data standards prevents healthcare providers from sharing medical records for continuing care, a critical challenge for decentralized systems like Wireless Access for Health (WAH). By mandating a "common data language" through the National Health Data Dictionary (NHDD), the order ensures that health data—whether from a rural health unit or a tertiary hospital—can be analyzed for national program planning and decision-making.
Furthermore, the JAO defines interoperability through a structured set of National Health Data Standards, which include specific data elements, official definitions, and standardized data types (e.g., text, numeric, and date formats). This policy framework supports the "FAIR" principles (Findable, Accessible, Interoperable, and Reusable) discussed by Vorisek et al. (2022) by providing the legal requirement for systems to utilize authoritative terminology services. For local health initiatives, compliance with these standards is now a prerequisite for licensing and accreditation, effectively making technical interoperability a mandatory operational standard rather than an optional technical feature (DOH & PhilHealth, 2021).


The global trajectory of healthcare informatics is increasingly defined by the transition from localized data digitization to the pursuit of semantic interoperability. As highlighted by Balch et al. (2023), while the post-HITECH era has catalyzed the widespread adoption of Electronic Health Records (EHRs), the clinical utility of this data remains hindered by fragmented architectures and variable implementation methods. The study posits that the lack of standardized data formats across institutions creates significant barriers to real-time clinical analysis and multi-institutional research. To mitigate these "data silos," the Fast Healthcare Interoperability Resources (FHIR) standard has emerged as the premier technical framework for achieving a unified data language. By utilizing a "resource-based" approach, FHIR provides the necessary modularity to transform disparate clinical narratives into structured, machine-readable formats, ensuring that health data is not merely digitized but truly interoperable (Balch et al., 2023).
Furthermore, the research underscores that the adoption of FHIR is a foundational requirement for the advancement of Machine Learning-enabled Clinical Information Systems (ML-CISs). By evaluating 39 distinct systems, the study categorizes these technological advancements into three functional domains: clinical decision support systems, data management and analytic platforms, and auxiliary modules or application programming interfaces (APIs). This taxonomy demonstrates that the "FAIR" principles (Findable, Accessible, Interoperable, and Reusable) are realized through the automation of data mapping and the reduction of manual pre-processing (Balch et al., 2023). Despite these advancements, many intelligent systems continue to face critical challenges regarding external validation and seamless integration into existing clinical workflows. Consequently, the findings suggest that the future of digital health lies in the development of secure, scalable, and interinstitutional data exchange protocols that can accommodate diverse electronic health record platforms (Balch et al., 2023).

Proposed Solution
Technical Background
To resolve manual bottlenecks within the WAH network, the proposed solution introduces a specialized AI automation function named ADAPT (Automated Data Processing and Transformation). ADAPT functions as an Integration Platform as a Service (iPaaS) and an Intelligent Middleware Endpoint. It is important to note that our scope is strictly building this iPaaS middleware. Establishing the actual connections, configuring the outbound webhooks, and providing the official iHOMIS API keys for deployment will be the sole responsibility of the Batch 1 team and WAH administrators.
1. Software Technologies
•	AI Orchestration Engine: To power ADAPT during the testing and prototyping phase, the system utilizes the Gemini API via a smart router function, primarily using Gemini 3.1 Flash Lite and Preview for high-volume translations. However, for actual clinical deployment, WAH will provide their own official, production-grade AI model to plug into the ADAPT architecture to ensure strict, localized data privacy compliance.
•	AI Tooling (Model Context Protocol): The Gemini models are controlled through an MCP server. This allows the AI to use specific tools, such as the SourceDataParser, to understand WAH4H data and the FHIRMappingTool to generate valid PH Core JSON files.
•	Consent-as-Code Module: This automated filter scans record metadata for a "Consent Flag" before any AI processing begins. If the flag is missing, the mapping function is blocked to ensure compliance with the Data Privacy Act.
•	Structural Validation Module: All AI-translated resources are automatically checked against the PH Core FHIR schema. Records missing critical data, such as PhilHealth IDs or birthdates, are quarantined for manual review.
2. Hardware Technologies
•	Go (Golang) Middleware: The "model juggling" logic is written in Go to take advantage of its high-speed concurrency. This allows the system to switch models in milliseconds without dropping the data payload.
•	API Load Management: The system is hosted on the existing Batch 1 Proxmox cloud environment. It uses secure API keys to connect to Google’s AI endpoints, ensuring that even during model switching, the data remains encrypted and protected.
3. Peopleware
•	AI Integration Engineers: Personnel responsible for prompt engineering and API management using Gemini 3.1 Preview to ensure mapping accuracy.
•	Data Quality Administrators: IT staff who monitor the automated quarantine logs and manually review records that fail the structural validation check.
•	Systems Integration Leads: Staff focused on maintaining the connection between the AI endpoint and the existing Batch 1 MongoDB repository and FHIR server.




4. Network Technologies
•	Secure Middleware Endpoints: The system operates as a RESTful API middleware. It receives raw data via HTTPS and sends validated FHIR resources to the central server using Transport Layer Security (TLS).
•	Encrypted Tunneling: While our group does not build the security layer, the automation endpoint is designed to operate within the secure VPN tunnels provided by the parallel security team.

Feasibility
Operational Feasibility
WAH4PCE project rests on its ability to seamlessly integrate into the daily workflows of rural health units and district hospitals without disrupting patient care. Currently, healthcare workers frequently struggle with the administrative burden of double data entry, manually inputting patient records into the local Wireless Access for Health (WAH) platform and then duplicating that data within the Department of Health’s (DOH) Integrated Hospital Operations and Management Information System (iHOMIS) for referrals or admissions. 
By establishing an automated interoperability bridge, the system operates invisibly in the background, minimizing data entry errors, eliminating redundant administrative tasks, and speeding up client processing times. Because medical staff are already deeply familiar with their respective platforms, user resistance will be minimal, and training will focus strictly on verifying data-syncing statuses and processing digital data privacy consent forms. 
Furthermore, this initiative directly aligns with the organizational mandates of Universal Health Care (UHC) in the Philippines, ensuring strong backing from local government health boards, hospital administrators, and the DOH, provided strict protocols are established to maintain compliance with the Data Privacy Act of 2012 (RA 10173).

Economic Feasibility
From an economic perspective, the financial viability of the project is highly secure, as the WAH Non-Government Organization (NGO) has officially committed to absorbing all core capital and operational expenses. A significant portion of the upfront infrastructure cost is already eliminated because the WAH NGO is providing a dedicated local server to host the integration system. Financial planning and the integrated AI models will therefore focus heavily on predicting, tracking, and optimizing operational expenses, such as long-term data bandwidth costs, local server power efficiency, hardware maintenance, and emergency IT support.
 By eliminating expensive proprietary software licensing fees through the use of open-source and custom-built tools, the financial risks are remarkably low. In return, the financial benefits to the public health system remain substantial; automating the data pipeline saves hundreds of collective clerical hours across municipal health centers, translating directly into optimized personnel allocation, faster referral windows, and a significant reduction in rejected PhilHealth claims.

 
Technical Feasibility
The technical feasibility of connecting WAH to iHOMIS is exceptionally strong, utilizing a modern, scalable, and high-performance technology stack deployed directly onto the local server provided by the WAH NGO. The user-facing configuration and monitoring dashboards will be built using Next.js for a responsive, modern front-end experience, while the core interoperability bridge, API routing, and data-mapping services will be handled by Go (Golang) to ensure ultra-low latency and highly efficient concurrent processing. For the data layer, MongoDB will be utilized as a flexible, document-based database capable of efficiently handling disparate, semi-structured health records and transaction logs before they are transformed. The local server will host this full-stack environment alongside the integration middleware that maps local data to the DOH iHOMIS backend. 
To ensure strict adherence to national health data standards, the Go backend will explicitly reference the HL7 FHIR R4 framework and the Philippine FHIR Core (PH Core) profiles to programmatically transform and translate incoming data payloads into standardized, compliant JSON health resources. To address the infrastructure challenges of remote Philippine municipalities, the Go backend will run a robust "Store-and-Forward" mechanism, allowing data to be queued securely in MongoDB when internet connectivity drops and automatically synchronizing it with the DOH endpoints once the wireless connection is restored. Security is tightly integrated, utilizing TLS 1.3 encryption for data in transit, cryptographic protection for data at rest on the local server, and strict access controls via OAuth 2.0.

Schedule Feasibility
		The schedule feasibility is highly viable, structured as a one-year project that strictly adheres to the systematic stages outlined in the academic course flowchart. The project lifecycle is divided into clear milestones across the year to ensure a logical transition from ideation to deployment.
•	Research & Development (Term 1): The initial phase is dedicated entirely to core R&D, where the research team will conceptualize the interoperability bridge, analyze the data endpoints of both systems, and formulate a comprehensive structural blueprint for the integration architecture.
•	Design & Prototyping (Term 2): Building on this conceptual foundation, the team will design detailed system, architectural, and data-flow diagrams to map WAH structures to the PH Core and HL7 FHIR R4 standards. This phase culminates in the construction of a working prototype to validate the data transformation logic and local server communication.
•	Development & Technical Documentation (Term 3): The final phase focuses heavily on full-scale development, implementing the production-ready Next.js frontend, Go backend, and MongoDB database on the WAH-provided local server. Parallel to code development, rigorous system documentation will be compiled, covering API endpoints, data transformation pipelines, security audits, and deployment guides to ensure system sustainability.
